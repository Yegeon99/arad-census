### 넘침·겹침 검사기를 새로 만들었습니다

`report/scripts/overflow-check.mjs`. 글자를 키운 뒤 무엇이 밖으로 나갔고 무엇이
서로 부딪는지 봅니다. 네 가지를 봅니다.

1. 문서가 가로로 넘치는지
2. 화면 밖으로 나간 요소가 있는지 (가로 스크롤 상자 안은 뺍니다)
3. SVG 글자가 제 그림틀(viewBox) 밖으로 나갔는지
4. SVG 글자끼리 겹치는지

만들면서 밟은 자리 둘을 적어 둡니다.

- **이 리포트는 해시 라우팅입니다.** `/growth` 로 가면 첫 화면이 나옵니다.
  `#growth` 로 가야 합니다. 처음에는 이걸 놓쳐 일곱 화면을 다 첫 화면으로 검사하고
  있었습니다. 예전 `reduced-motion.mjs` 의 사각지대와 같은 종류입니다.
- 검사기를 만들면 **일부러 망가뜨려 잡히는지 먼저 확인**하십시오. 넘치는 상자와
  그림틀 밖 글자와 겹친 글자를 심어 세 가지 다 잡히는 것을 보고 나서 믿었습니다.

`verify_final.py` 의 차트 글자 겹침 검사는 활성도 화면의 그 1픽셀 겹침을 못 잡았습니다.
`stability.mjs` 는 잡았습니다. 겹침을 볼 때는 이 둘을 같이 돌리십시오.

## 끝난 것: 빠른 스크롤에서 화면이 비어 보이는 문제

2026년 9월 1일에 마무리했습니다. 아래는 원인과 고친 방법의 기록입니다.
손댄 파일은 다섯입니다.

- `report/src/lib/reveal.js`
- `report/src/lib/admit.js`
- `report/src/lib/hooks.js`
- `report/scripts/stability.mjs`
- `docs/stability.json`

### 무엇을 하던 중인가

지시받은 세 가지였습니다.

1. 등장 관찰 범위를 화면 아래 300픽셀까지 넉넉히 잡기 → `ENTER_LEAD = 300` 넣음
2. 화면에 들어온 뒤 400밀리초 마지노선 → `VISIBLE_MS = 400` 넣음
3. 빠른 스크롤(초당 화면 3개) 검사를 표시 안정성에 추가 → 넣음

### 검사를 만들다 알게 된 것

처음 만든 검사는 헛돌았습니다. 다 훑고 잦아든 화면에서 재고 있었기 때문입니다.
갓 들어온 화면에서 곧바로 내리도록 고치고, CPU 4배 저속 조건을 붙이자
**진짜 결함이 잡혔습니다.** 화면당 1~5번씩 본문 자리가 통째로 비었습니다.

원인은 지시받은 두 가지가 아니라 세 번째였습니다. 진입 연출은 요소마다
최대 350밀리초를 기다렸다 시작하는데(`STEP_MS` 간격), 그 사이에 스크롤이
들어오면 그 화면 전체가 아직 투명한 상태로 지나갑니다. 300픽셀을 앞당겨도
초당 화면 3개 속도에서는 0.11초밖에 못 법니다.

### 마지막으로 한 수정 (아직 확정 아님)

등장 판정을 두 단계로 갈랐습니다 (`reveal.js`의 `whenInView`).

- **시작선** 화면 아래 300픽셀: 등장 연출을 시작한다
- **마지막선** 화면 아래 그 자리: 연출이 어디까지 갔든 그냥 다 보이게 한다

마지막선은 스크롤이 들어온 그 순간 셈해서 켭니다(`sweep`을 다음 그림에
미루지 않고 스크롤 이벤트에서 바로 돌림). 다음 그림을 기다리면 느린 기기에서
수백 밀리초 밀리고 그동안 그 자리가 빕니다.

이 수정을 넣고 표시 안정성 **14/14 통과, 빈 화면 0번**이 한 번 나왔습니다.
그 전 수정들에서는 **회차마다 결과가 달랐습니다** (같은 코드로 0번, 2번, 4번).
그래서 확정 전에 `node scripts/stability.mjs` 를 세 번 연속 돌렸고,
세 번 다 빈 화면 0번이었습니다.

### 확인한 것

- 표시 안정성 **3회 연속 통과**, 빠른 스크롤 176번 들여다봄, 빈 화면 0번,
  마지노선 넘겨 안 보인 요소 0건. 걸리는 회차가 있으면 `docs/stability.json` 의
  `fastBlanks` 에 위치와 그때 상태(`inView`, `textEls`, `faded`)가 남습니다.
- `node scripts/perf-block.mjs 20 4` 통과. 가장 긴 멈춤 172밀리초 (기준 200).
- 전체 검수 통과. `npm run build`, `build-copy`, `capture`, `font-check`,
  `reduced-motion`, `render-audit`, `verify_final.py`(검사 166건 실패 0),
  `verify_findings.py`(대조 41건 불일치 0), `check_docs_links.py`(문제 0).
  `render-audit` 의 실패 2건은 아래 "13픽셀보다 작은 글자"뿐이고 수치도 그대로입니다.
- README 와 `docs/findings.md` 의 이름과 주소가 DNF Census /
  dnf-census.vercel.app 으로 통일돼 있는지 대조했습니다. 옛 표기 0건.

### 걷어낸 것과 남긴 것 (검사로 가렸습니다)

원인을 찾는 동안 넣었다가 효과가 확실치 않던 세 가지를, 하나씩 빼고
표시 안정성 검사를 세 번씩 돌려 가렸습니다.

- `reveal.js` 의 `showRightAway` (이미 화면에 든 요소는 숨기지 않음) — **걷어냄**.
  빼고 3회 모두 빈 화면 0번. 딸린 `lastScrollAt`, `SCROLLING_MS`, `NEAR_SCREENS`도
  함께 지웠습니다.
- `admit.js` 의 `PACE` (시간이 갈수록 한 프레임에 여러 개 들여보냄) — **걷어냄**.
  빼고 3회 모두 빈 화면 0번. 이제 언제나 한 프레임에 하나씩입니다.
  읽는 곳이 없어진 `backlogAt`도 함께 지웠습니다.
- `admit.js` 의 `RUSH_MS` 와 `calmDown` (스크롤 뒤 한동안 곧바로 그림) — **남김**.
  빼자 3회 중 2회에서 결함이 되살아났습니다 (모바일 인사이트 화면, 빈 화면 1번).
  이것 하나가 실제로 결함을 막고 있습니다.

`reveal.js` 에서 아무도 쓰지 않게 된 `framePending` 도 지웠습니다.

걷어낸 뒤 표시 안정성 3회 연속 통과(빈 화면 0번), `perf-block.mjs 20 4` 통과
(가장 긴 멈춤 172밀리초, 기준 200).

인사이트 재생성은 이미 끝났으므로 지금 교체해도 작업에 지장 없습니다.

## 성능 작업 기록

### 판정

`node scripts/perf-block.mjs 20 4` (CPU 4배 느리게, 상황마다 20회) **통과**.

| 상황 | 고치기 전 | 고친 뒤 | 기준 초과 |
|---|---|---|---|
| 한눈에 보기 진입 | 458밀리초 | **149밀리초** | 0/20회 |
| 조사 방법 진입 | 192밀리초 | **134밀리초** | 0/20회 |
| 한눈에 보기 스크롤 | 0밀리초 | 0밀리초 | 0/20회 |
| 성장 단계 스크롤 | 0밀리초 | 0밀리초 | 0/20회 |
| 성장 단계 보정 전환 | 0밀리초 | 0밀리초 | 0/20회 |

앞 회차 기록의 470과 397밀리초는 다른 기기에서 잰 값입니다. 견주기 위해
이번 기기에서 고치기 전 상태를 다시 재서 458밀리초를 기준으로 삼았습니다.

### 원인 두 가지와 고친 방법

**하나. 등장 연출이 요소마다 위치를 물어 배치를 강제로 돌리고 있었습니다.**

프로파일에서 자기 시간 353밀리초를 한 함수가 쓰고 있었습니다.
`reveal.js`의 `docTop`, 곧 `getBoundingClientRect`입니다.
등장 연출은 요소가 올라올 때마다 모양을 손대고(투명도와 위치) 곧바로 위치를 물었습니다.
손댄 직후에 물으면 브라우저는 그 자리에서 배치를 다시 계산합니다. 요소 수만큼
되풀이되니 그것만으로 0.35초가 갔습니다.

고친 방법: 위치를 재는 일을 등록할 때가 아니라 실제로 스크롤이 일어난 뒤로 미루고,
잴 것을 한 번에 몰아서 잰 다음 켭니다 (`report/src/lib/reveal.js`).
화면에 걸쳐 있는 요소는 어차피 교차 관찰자가 알려 주므로 잴 일 자체가 없습니다.

**둘. 화면 하나를 한 번에 다 그리고 있었습니다.**

첫 번째를 고치고 나니 남은 비용은 배치 계산 그 자체였습니다. 트레이스로 보니
한 작업 안에서 문서 전체 배치가 한 덩어리로 돌고 있었습니다 (432밀리초).
리포트 한 화면은 세로 3천 픽셀이 넘는데, 눈에 보이는 것은 900픽셀뿐인데도
전부를 한 번에 계산했습니다.

고친 방법: 묶음을 한 프레임에 하나씩 들여보냅니다
(`report/src/lib/admit.js`, `Stagger`가 씁니다). 배치 계산이 묶음 수만큼 잘게
나뉘어 한 번에 붙잡는 시간이 짧아집니다. 전부 들어오기까지 걸리는 시간 자체는
거의 그대로입니다.

곧바로 그리는 묶음을 몇 개 둘지도 재봤습니다. 하나도 두지 않는 쪽이 가장
좋았습니다. 0개면 136밀리초, 1개면 188, 2개면 260, 3개면 241입니다.
제목 묶음 하나만 곧바로 그려도 첫 배치에 제목 글꼴 처리가 함께 걸려 다시
무거워집니다. 사람 눈으로는 한 프레임 차이라 알아볼 수 없습니다.

만들면서 어긋났던 곳 두 가지를 적어 둡니다. 같은 방식을 다시 만들 때 그대로
밟게 되는 자리입니다.

- 차례를 돌리는 일을 자리를 받을 때만 걸어 두면, 기다리겠다는 등록이 들어오기
  전에 차례 돌리기가 끝나 버립니다. 그러면 남은 묶음이 영영 안 들어와 화면이
  제목만 남습니다. 등록하는 자리에서도 다음 차례를 불러야 합니다.
- 그리는 사이에 차례가 지나간 묶음이 생깁니다. 그리기와 등록 사이에 한 프레임이
  끼기 때문입니다. 이것을 그냥 흘려보내면 그 묶음만 빈 채로 남습니다.
  실제로 한눈에 보기에서 카드 한 장과 숫자 한 칸이 빠졌고, 화면 문구 전문을
  대조해서 잡았습니다. 지나간 묶음도 줄을 세워 다음 프레임에 켭니다.

### 재본 뒤 아니라고 판명된 것

같은 조건에서 재보고 원인이 아니라고 확인한 것들입니다. 다시 뒤지지 않도록 남깁니다.

- 자바스크립트 파싱과 컴파일. 앞 회차에서 남은 몫으로 지목했지만 아니었습니다.
  진입 구간의 배치 계산이 몫의 대부분이었습니다.
- 차트. 한눈에 보기에서 차트를 통째로 들어내도 배치 비용이 그대로였습니다.
- 격자와 신축 배치, 아이콘 도형, `word-break`와 `overflow-wrap`.
  각각 무력화해 봤지만 모두 오차 범위였습니다.
- `content-visibility: auto`. 405에서 353밀리초로 조금 줄지만, 화면 밖 내용을
  그리지 않는 방식이라 전문 뽑기와 캡처에 위험이 있어 넣지 않았습니다.
  묶음을 나눠 들여보내는 방식과 겹쳐 써도 248에서 246으로 거의 그대로였습니다.

### 손대지 않은 것 (판단이 필요합니다)

진입 비용에서 지금 가장 큰 몫은 **첫 배치의 글꼴 처리**입니다. 다만 화면 생김새가
걸린 문제라 임의로 바꾸지 않았습니다. 서브셋 방식 자체는 이미 유니코드 범위 분할이라
바꿀 것이 없었습니다. 위 "글꼴은 이미 유니코드 범위 분할이었습니다" 참고.

- 이 화면은 글꼴 조각 파일을 33개, 991킬로바이트 받습니다.
  조각이 하나 도착할 때마다 문서 전체 배치가 다시 돕니다.
- `@font-face` 규칙이 340개입니다 (Pretendard 92, Noto Serif KR 248).
  같은 조건에서 재보니 규칙 수만으로 첫 배치에 35밀리초가 붙습니다
  (0개 24밀리초, 340개 59밀리초).
- 남은 방법은 두 갈래입니다. 제목용 세리프의 굵기를 400과 700 둘에서 하나로 줄이거나,
  `font-display`를 `optional`로 바꿔 늦게 온 글꼴로 바꿔치기하지 않게 하는 것입니다.
  둘 다 화면 생김새가 바뀝니다. 글자만 뽑아 조각을 직접 만드는 `text=` 방식은
  글자별 누락이 생기므로 쓰지 않기로 했습니다.
- 글꼴 CSS를 렌더 차단으로 되돌리면 240에서 206밀리초로 줄지만, 바깥 CDN 응답이
  늦으면 첫 그림이 통째로 늦어집니다. 지금 방식(늦게 걸기)을 그대로 두었습니다.

### 재현되지 않은 것

**보고받은 30초 멈춤은 이번에도 재현하지 못했습니다.** 스크롤과 클릭 구간은
CPU 4배와 6배 저속 조건에서 모두 0밀리초입니다. 잡아서 고친 것은 진입 구간이고,
그것이 30초 멈춤과 같은 원인인지는 확인되지 않았습니다.

- 30초 멈춤이 **첫 진입 직후**였는지, **한참 보고 있다가**였는지
- 첫 진입 직후라면 지금 고친 것과 같은 원인일 가능성이 높습니다
- 한참 뒤였다면 다른 것을 찾아야 합니다 (메모리 누수, 관찰자 누적 등)

## 이름과 주소

  저장소 `arad-census`는 301로 넘어갑니다. 한 주소로 수렴합니다.
- 배포 점검(`report/scripts/check_prod.mjs`)이 화면에 옛 이름
  (`ARAD CENSUS`, `Arad 센서스`, `Arad Census`, `아라드 센서스`)이 남아 있으면
  실패로 잡습니다.

세계관 서술의 "아라드"는 프로젝트명이 아니므로 바꾸지 않습니다.
이번 검출에서는 세계관 용어로 쓰인 "아라드"가 저장소와 배포본을 통틀어 0건이었고,
검출된 것은 모두 프로젝트명이었습니다.

## 이번 판에서 알아 둘 것

### 다시 만들 수 없는 것 두 가지

개인정보 방침에 따라 원본 표본(`data/checkpoints/`)을 이미 폐기해서
2차 기준으로는 계산할 수 없습니다. 그래서 화면에서 걷어냈습니다.

- 성장 단계 화면 하단의 명성 히스토그램. 1만 단위로 세려면 원본 명성값이 필요합니다.
  그 자리는 상한 보정 근거 절로 대체했습니다.
- 직업군 막대 안의 전직 칸. 남녀가 나뉜 직업군은 전직 이름이 같아 집계만으로는
  어느 쪽인지 가릴 수 없습니다. 직업군 크기만 그립니다.

### 실측치 표의 셈법

이번 판 여섯 항목 합계가 18,462회입니다.
처음 조사 커버리지 측정 867, 시드 고르기 867, 커버리지 측정 867, 표본 수집 8,001,
상한 우회 7,200, 활성도 조사 660.
명성 방식 검증 947회와 처음 조사 933회는 이번 판 이전 것이라 별도 줄로 두었고,
모두 합치면 20,342회입니다.

### 문구 규칙

쉬운 말, 줄표 금지, 코드 식별자 금지, 의문형 소제목 금지입니다.

검사 규칙에 예외를 두어야 합니다. 본인 판단을 아직 못 받았습니다.

## 자주 쓰는 명령

```bash
# 리포트 빌드와 검수
cd report
npm install
npm run build                  # 집계 파일을 화면 용어로 바꾼 사본을 먼저 만든다
node scripts/build-copy.mjs    # 화면 문구 전문 뽑기
node scripts/capture.mjs       # 캡처와 화면 글 모음
node scripts/stability.mjs     # 표시 안정성 14가지
node scripts/font-check.mjs    # 세리프 글자가 폴백으로 안 떨어지는지
node scripts/check_prod.mjs    # 배포본 확인

# 성능
node scripts/perf-block.mjs 20 4        # 상황별 멈춤, 20회 반복
node scripts/perf-profile.mjs enter-overview 4   # 어느 함수가 잡아먹는지
node scripts/perf-layout.mjs overview 4 200      # 스크롤당 레이아웃 횟수
node scripts/perf-live.mjs https://dnf-census.vercel.app 6   # 배포본을 실제 창으로

# 데이터와 문서 대조
cd ..
python scripts/verify_final.py       # 집계, 화면 숫자, 금지 표현, 표시 안정성
python scripts/verify_findings.py    # 문서 인용 수치와 산출물 대조
python scripts/check_docs_links.py   # 문서 링크와 이미지
```
